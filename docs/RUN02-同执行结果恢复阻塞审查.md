## 要求及已确认事实

- 产品需求文档 RUN 02：待下载／下载失败的前提是远端视频已经生成，重试下载或导入沿用同一次生成。RUN 03 要求结果不明先核实；主动重做才创建新执行。OUT 01 要求本地文件可访问后才完成。
- `src/main/infrastructure/database.ts`：V7 的 executions 仍只有通用 `operation/status/input_json/remote_reference/account_id` 等字段。状态和远端引用是文本；没有已验证远端生成结果、输出身份或恢复授权的专用证明。
- `src/main/infrastructure/workspace-repository.ts` 的 snapshot 只将非空 remote_reference 投影为 `hasRecordedRemoteReference`；该布尔值不是经过认证的远端任务，更不是视频完成／可下载证据。
- `src/shared/execution-recovery.ts` 明确把 completed 解释为“本地记录为完成”，不核验远端结果或成片文件；未知状态保守呈现。不能因为 completed、generating、非空 reference 或某个 JSON 字段看似成功，就标为可恢复下载。
- `src/shared/submission-result.ts` 和 `submission-reconciliation.ts` 只是未持久化的内部纯契约。accepted 仅受理同一次尝试，所有有效分支仍 `videoCompleted:false`；可信协议适配器、身份认证与完整证据持久化并未实现。参数声明 `verified-acknowledgement` 不是实际认证。
- `local-film-record.ts` 当前只写中性 local-import / recorded，remote_reference 与 account_id 均为空；其随机新执行不是原远端执行，不可用于 RUN 02 恢复。

**结论：现有 V7 字段和类型无法证明一个具体执行已产生某个可保存的远端视频。当前不能提供“可恢复下载”的可操作资格标签。** 不新增一个永远拒绝的重复预检查，也不伪造成功字段或将纯契约接成恢复授权。

## 下一步最小可信边界

以下是设计必须回答的输入与绑定要求，不是已经确定的新数据库字段或迁移方案：

1. **原执行归属**：可信应用持有原 execution、task、实际生成 account、提交尝试及当时输入快照的稳定绑定。不能靠当前任务修订重建旧输入；不能用其他账号／执行结果替代。
2. **生成完成证据**：真实已验证的接入模块必须能区分“受理”“生成中”“明确生成失败”“生成完成”，记录证据来源／校验方式／观测时点及同一远端任务身份。冲突／过期／无法核实必须停止，不采用最后响应覆盖规则。
3. **输出身份**：同一远端任务的明确视频输出标识（含版本／候选身份，如官方提供）、来源约束，以及取得字节后如何证明属于该输出。下载 URL 本身可能含凭据或过期参数，不能当公开标签、稳定身份或恢复许可；也不能预设服务必有摘要／免费导出能力。
4. **本地导入归属**：用户选择一个 MP4 或它能解码，仅证明选中文件可检查，不证明来自原生成。必须先确定服务可提供何种可信输出对应证据；无法证明时只能作为独立本地附件，不能冒充原执行恢复完成。
5. **同执行事务**：验证上述身份后才可计划沿用原 execution 的保存与成片登记，拒绝重复目标／已有不一致版本。不得调用当前创建新 local-import 执行的事务，也不得触发新提交；物理发布和 SQL 不确定结果需要单独对账，不能重放副作用。
6. **重启／备份边界**：恢复的本地记录是历史元数据，不重新授予平台会话、下载能力或已验证文件权限。原生当前应用、账号及输出重新核验和 V7 备份／隔离恢复兼容规则必须先定，再决定是否新增持久化结构。
