# F19 本地命令诊断边界

本轮只加固已有命令日志和本地保存失败证据，不提前实现真实生成／下载诊断，不新增远端遥测或日志上传。

## 审查发现

原命令路由已只记录请求编号、操作类别、结果、耗时和错误类型，不记录请求正文。但文件日志器直接展开传入对象，不能阻止以后调用者携带额外字段；磁盘写入失败时还直接输出未经边界筛选的字段。另一个确定性问题是日志器抛错可以进入命令业务错误分支，甚至使已经提交的操作被回报为失败。日志目录初始化失败也可能阻断工作区启动。画布自动保存失败则只保留错误文字，丢失了命令返回的请求编号。

## 本轮目标与边界

- 日志落盘采用明确字段白名单，操作与错误类型使用有限类别；无效值不能变成任意文本日志。
- 保留合法请求编号以关联用户失败反馈与命令；未知操作归为无效类别，不记录原始命令字符串。
- 脚本／提示词／账号资料／凭据／完整文件路径／异常消息、堆栈、嵌套对象等不进入诊断记录。
- 日志写入和兜底输出使用相同脱敏元数据。日志自身失败不能改变已提交业务结果，也不能破坏正常错误响应或重试回执。
- 自动保存保留格式有效的 UUID 请求编号，在画布保存失败处展示；继续编辑不丢失诊断编号，显式重试或冲突处理后清除旧编号。非法编号不作为可复制诊断标识展示，草稿和失败重试规则保持不变。
- 日志目录创建为尽力而为，不再作为工作区路径初始化的必需成功条件；数据和素材目录仍须正常创建。日志目录不可用时只给出脱敏的本地兜底反馈。
- 数据库中的业务记录和幂等回执并非诊断日志，仍会保存正常业务内容。本轮不扫描或改写用户正文，也不声称把业务数据库变成脱敏数据库。

## 验证范围

仅合成 SQLite、临时日志目录与假的故障输入；不使用真实用户内容、凭据或账号。通过实际命令保存、失败回滚与日志故障组合检查元数据、结果和回执是否一致。新增 5 项诊断回归及 2 项自动保存回归。最终全量 `npm test` 165/165（0 失败、0 跳过），独立 `npm run typecheck`、`npm run build` 与 `git diff --check` 均通过。既有第三方 `use no memo` 构建警告不阻断通过。

覆盖额外字段／自定义 toJSON／非法类别与编号／异常载荷均不落日志；真实文件及控制台兜底内容；坏目录／坏 stderr；日志同步抛错和异步拒绝时提交、回执重放及冲突结果不变；真实路由错误的编号／类别可关联；日志路径被普通文件占用时数据库和媒体目录仍可初始化；自动保存失败编号与草稿保留、非法编号丢弃及重试／冲突处理清除。独立只读复审无新增阻断，内存定向 3/3 独立通过；文件测试由实现线程及主工程线程完整执行，未运行原生 UI。

真实生成步骤、任务／执行／账号／成片的完整诊断关联及恢复操作仍待开发。未运行 Windows 或真实 UI 验收，F19 仍为 L2 部分完成。
